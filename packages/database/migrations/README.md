Migration `005_staff_workflow_persistence` registers the local **non-authorized** workflow foundation (ADR 0018): eleven immutable FORCE-RLS artifact tables, fixed audit/receipt/outbox bindings, synthetic provenance and two SECURITY INVOKER functions including an always-deny command gate. The three unchanged pending SQL files are historical rehearsal evidence and are no longer loaded by workflow acceptance. No effective staff/grant changes or accepted approvals exist.

005 rejects non-loopback/non-5432 and unapproved disposable names. Actual fixture creation/owner/role/target checks are still required; naming is not authority. Only verified disposable tests may apply it. Existing `nukhabapay_dev` remains on 001–003. The default migrate script discovers 005 and must not be run against development. IAM-only regressions use `up 4 --timestamp`; workflow acceptance runs `up 5 --timestamp` with the same single-transaction/order/history settings. Migration replay is a history no-op, not rerunning CREATE statements. Failed 005 up rolls back DDL/defaults/history; automatic down refuses to delete immutable history. Separately approved restore is required after committed deployment; it is not tested here.

No runtime role is created or granted access by 005. Owner-operated `../roles/grant_staff_workflow_backend.sql` selects an already provisioned restricted generated login inside a verified disposable transaction. See ADR 0018 for exact six/optional seventh table grants, 27 IAM columns, tenant policies and cleanup requirements. Existing IAM/catalogue rights remain unchanged. PUBLIC and workload future table/function defaults are revoked globally and in-schema; new objects explicitly revoke those principals. Any remaining unknown default grantee rejects the migration and rolls back instead of acquiring artifact access. Future schema changes belong in a separately approved later migration, not an extension of 005 into privileged execution.

The numbered migrations are the schema history; `001_catalog`, `002_import_role_privileges`, and `003_import_role_read_access` implement the local catalog and restricted importer. Migration `004_staff_identity_foundation` adds provider-independent staff identity bindings, memberships, fixed scoped role/permission data, separate platform/tenant grants, and append-only security-audit persistence. It also enables forced tenant RLS for memberships, tenant grants, and tenant-associated audit records. It does not configure an identity provider, implement token validation, or add staff/grant management operations.

Migration 004 is exercised on fresh disposable PostgreSQL databases and rerun there for idempotent migration behavior. It has not been applied to the existing `nukhabapay_dev` database. The test administrator seeds synthetic fixture rows because `FORCE ROW LEVEL SECURITY` also constrains table owners; application behavior is separately tested using the restricted identity reader and audit writer logins.

`node-pg-migrate` ignores non-numeric documentation files via the package script so migration discovery remains deterministic. Check the target database's `schema_migrations` history before assigning another migration number.

The pending 004 migration was corrected during the 11 November 2026 recovery after read-only history confirmed it absent from `nukhabapay_dev`. It removes catalogue runtime/importer default table grants before IAM creation and explicitly revokes catalogue/PUBLIC access on all nine IAM tables. Existing catalogue grants and forced tenant RLS remain intact. Future module tables require explicit grants. Real-role acceptance checks all IAM read denials, exact IAM column rights and a migrator-created default-grant probe. See `docs/verification.md`; no automatic development migration is authorized by these results.
