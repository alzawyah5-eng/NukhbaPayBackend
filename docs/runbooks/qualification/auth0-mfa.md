[Transaction metadata](https://auth0.com/docs/customize/actions/transaction-metadata) · [Post-Login event object](https://auth0.com/docs/actions/reference/post-login/post-login-event-object) · [Auth0 request lifecycle](https://support.auth0.com/center/s/article/event-request-query-is-overwritten-between-post-login-actions-after-a-mfa-challenge)
3. The later Action can emit authenticated evidence in an owner-namespaced custom ID-token claim with `api.idToken.setCustomClaim`. The owner's versioned claim contract must specify provenance, factor identity, completion time and challenge correlation. The backend validates the signed ID/access-token pair and nonce and looks up the exact command in its one-use callback transaction. The command payload and durable approval/replay records belong to the backend. [Auth0 custom ID token claims](https://support.auth0.com/center/s/article/Set-ID-token-claims-using-actions)

Auth0 tenant logs supply an event-record `log_id` and can corroborate the pilot. A lookup would need an authenticated tenant source and demonstrated correlation to the exact challenge and completed factor. Subject, client and timestamp proximity alone are insufficient. The backend consumes the verified event ID in the same disposable database transaction as the effect. A cold BFF instance requires a new session and challenge. The consumed event remains recorded across replicas and restarts of the BFF.
