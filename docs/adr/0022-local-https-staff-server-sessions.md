# ADR 0022: Local HTTPS staff portal and gated server sessions

Date: 12 November 2026. Status: implemented for local synthetic verification; operational activation remains blocked.

The owner authorizes only a minimal staff BFF, internal actor/version-bound sessions, audited revocation and disposable database acceptance. Real Auth0 login, accepted privileged approvals, APPLY, reserved permissions, real staff onboarding and financial execution remain disabled. Existing API authentication modes and JWT checks do not change.

Use Node 24's HTTPS server and strict TypeScript in the existing `apps/admin-web` workspace. The small static portal needs no new runtime framework. This avoids introducing a UI framework or an OIDC SDK before login is authorized. Browser code receives only a host-only session cookie and a session-bound CSRF value; it imports no backend package. Public assets are explicitly selected strings, not a filesystem static root. Future OIDC integration must use a maintained supported server SDK, not custom protocol or cryptography.

The CLI binds `127.0.0.1:3001`, advertises `https://localhost:3001` and has no session-store/actor/provider composition. Existing API remains `127.0.0.1:3000`. TLS startup validates the public localhost certificate and strictly probes its own HTTPS listener to verify the PFX, hostname and certificate agree. Private certificate material stays outside OneDrive/source/checkpoints, encrypted with a random passphrase protected by current-user DPAPI. A separate reviewed trust action installs only the public, 30-day, localhost-only, non-CA certificate in CurrentUser Root. The owner declined Windows trust installation in this increment. The optional trust action was not completed; Windows trust stays unchanged. The explicit pinned-client launcher mode uses strict certificate/hostname validation without claiming browser trust. Never disable peer verification or change LocalMachine trust/global execution policy.

The application session lifecycle is default disabled. Only explicit trusted internal synthetic composition can enable it. Existing opaque actors yield immutable runtime-registered, actor-bound evidence after fresh staff/identity/membership/version checks and committed authorization audit. Client JSON, IDs, MFA flags, copied evidence, another actor's proof or database rows cannot create that evidence. Sessions retain exact issuer/subject/canonical staff, tenant, staff/membership versions, a complete authority digest including time-dependent grant status, and verified identity expiry. No email linking, enrollment, authorization cache or new permission is added.

Use cryptographically random 256-bit session IDs and persist only SHA-256 identifiers. Internal credentials redact themselves in JSON/string/inspection output. Session creation has no supplied-ID parameter. Rotation creates a fresh ID and atomically revokes the previous generation; cross-person, identity and tenant rotations deny. Absolute lifetime is capped at eight hours and idle lifetime at fifteen minutes; each is persisted/enforced, and the effective lifetime is also bounded by the original verified access token (currently at most five minutes). No silent refresh exists. Observed status/scope/version/temporal-authority changes invalidate the local handle permanently and attempt audited durable revocation. Database/audit outages never create successful validation or unconfirmed logout results.

Proposed migration 006 stays outside the registered migration directory. It runs only on guarded disposable targets and adds a separate `nukhbapay_sessions` schema, two immutable FORCE-RLS tables, SECURITY INVOKER constraint/immutability functions, and one IAM consistency index needed for the exact staff/issuer/subject foreign key. Existing migrations 001–005, IAM/catalogue table grants and workload credentials remain unchanged. A separate ephemeral session backend has exactly 27 SELECT and 23 INSERT column grants, no table-wide grant, effective IAM access, mutation/DDL/role privilege or executable function grant. Existing authorization audit writers cannot emit session events or staff-success events through it.

Session rows and fixed `SESSION_CREATED`, `SESSION_USED`, `SESSION_REVOKED` audit events commit together. Deferred constraints require complete creation and rotation tuples. Append-only revocation prevents resurrection by rolling updates. READ COMMITTED transactions acquire sorted transaction advisory locks before fresh reads; the same per-session lock is checked by the event trigger. Use parameterized actor/hash/scope queries, finite timeouts and rollback/discard cleanup. Unknown commit acknowledgement returns failure; authoritative revocation lookup may subsequently confirm it. No raw credential is returned after uncertain creation/rotation. Workload credentials and RLS settings never prove a human actor.

The actor registry deliberately is not reconstructed from database data. A cold process rejects old cookies until a new trusted authentication ceremony. The bounded single-process registry (1,000 issued entries), original-token expiry cap, missing retention/HA/refresh implementation and synthetic-only SQL/runtime gates mean this is not an operational session service. Database credential possession alone cannot authenticate an injected session row. In-flight operations may have linearized before a revocation; no claim is made that logout cancels already completed work. Separate IAM freshness reads are not an atomic privileged-execution guarantee, and sessions never replace API authorization.

Cookie name is corrected to `__Host-nukhbapay_staff`: Secure, HttpOnly, SameSite=Strict, Path=/, no Domain. State-changing logout requires exact server origin, session-bound HMAC CSRF, a JSON empty object and bounded input. Existing global API guards are unchanged. Auth0 login/callback/access-token routes do not exist; future OIDC transaction cookies need separate reviewed SameSite handling for the cross-site callback. See [the session runbook](../security/staff-server-sessions.md) and the current verification record.
